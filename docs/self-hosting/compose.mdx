---
title: "Self-hosting with Docker Compose"
description: "Run a full LazyCloud installation on one machine with Docker Compose."
---

The repository's root `compose.yaml` is a complete single-machine
installation: control plane with the web dashboard, scheduler, workers,
container workers, PostgreSQL, Redis, S3-compatible object storage, and a
distributed cache filesystem.

## Prerequisites

- A checkout of the LazyCloud repository.
- Docker with the Compose plugin. Container workers run privileged (they run
  your workloads in nested containers).

## Start the stack

From the repository root:

```bash
umask 077
cp .env.example .env
python - <<'PY'
from pathlib import Path
import secrets

path = Path(".env")
contents = path.read_text(encoding="utf-8")
token = f"rt_{secrets.token_urlsafe(32)}"
path.write_text(contents.replace("LAZYCLOUD_TOKEN=\n", f"LAZYCLOUD_TOKEN={token}\n"), encoding="utf-8")
PY
chmod 600 .env
docker compose up -d --wait --build
```

The first start builds the service images. Each image has one build owner, so
rebuilding `control-plane` or `agent` does not build the privileged
container-worker toolchain. Use `docker compose build <service>` when only one
service image changed; a normal `docker compose up -d --wait --build` still
builds every required image.

The one-shot `database-bootstrap` job bootstraps an empty database, or verifies
that an existing database is already at the image's schema revision. It
deliberately refuses to migrate an older installation while writers are
running. The one-shot `administrator-bootstrap` job then creates the initial
administrator from the private Compose secret and stores only its hash in
PostgreSQL; it never copies or prints the configured token. Only
`administrator-bootstrap` receives the mounted secret; it is not an environment
variable in that container or any other service. Worker credentials are minted
only after that administrator exists. Re-running the stack reuses the same
administrator credential instead of rotating it. Recreating the disposable
database also restores the same development authority from `.env`.

The control plane (API and dashboard) listens on
`http://127.0.0.1:8000` by default. Change the port with
`LAZYCLOUD_COMPOSE_CONTROL_PLANE_PORT` in `.env` and pass the same endpoint at
login.

## Use the client

Install the public client. From a checkout of the LazyCloud repository — the
supported path until the beta release is published to a package registry —
install it from the repository root:

```bash
uv tool install ./packages/lazycloud
```

or build and install the wheel:

```bash
uv build --package lazycloud
pip install dist/lazycloud-*.whl
```

Run the public client from the repository root. Its normal settings loader reads
the private, mode-`0600` `.env`, so no login or credential-copy step is needed
and the token never appears in command arguments or output.

```bash
lazycloud workspace show
```

Separate ordinary-user profiles can run
`lazycloud login --endpoint http://127.0.0.1:8000` without a token and have an
administrator approve the displayed device code in the dashboard. Verify the
configured development authority:

```bash
lazycloud workspace show
lazycloud quickstart
lazycloud deploy quickstart.py:hello
lazycloud run quickstart.py:hello 'LazyCloud'
```

## Optional profiles

| Profile | Enables |
| --- | --- |
| `gpu` | A GPU container worker (`docker compose --profile gpu up -d`); size it with the `LAZYCLOUD_COMPOSE_GPU_*` variables in `.env`. |
| `tailnet` | The tailnet gateway for private connectivity to remote compute. |
| `tools` | The `cli` operator-tools container. |

## Operating the stack

Operators use the internal `lazycloud-admin` CLI from the tools container. The
repository is predeployment and supports one current schema only. The database
bootstrap job creates an empty database or verifies the exact current baseline;
it refuses a stale or unknown revision instead of attempting an upgrade.

When the schema baseline changes, stop the stack and recreate only an installation
you have positively identified as disposable. For the root development project,
`docker compose down -v` removes PostgreSQL together with the other coordinated
local state; the next `docker compose up -d --wait --build` starts from the fresh
baseline. Never use that reset command for a shared, external, or persistent
installation.

During this predeployment phase, every named volume owned by the root Compose
project is disposable. If Docker storage is full, stop the stack, inspect the
exact label-scoped set, and remove only volumes whose
`com.docker.compose.project` label is `lazycloud`:

```bash
docker compose down
docker volume ls --filter label=com.docker.compose.project=lazycloud
docker volume ls -q --filter label=com.docker.compose.project=lazycloud |
  while IFS= read -r volume; do docker volume rm "${volume}"; done
docker compose up -d --wait --build
```

The label filter does not select bind mounts, volumes from another Compose
project, or unlabeled storage. Review the listed names before running the
removal loop.

Routine operations:

```bash
docker compose ps                 # service health (all services expose healthchecks)
docker compose logs -f control-plane
docker compose down               # stop; add -v to also delete all data volumes
```

Durable state lives in named Docker volumes (PostgreSQL data, object storage,
image caches, and tokens). `docker compose down -v` destroys the entire local
installation.
