---
title: "Local, preview, deploy"
description: "The four ways to run a workload, what each one gives you, and how a call decides where to go."
---

The same decorated function runs four ways. Pick by what you need from the run:
your own machine for logic, a one-off remote run for the real image and
resources, a preview that reloads as you edit, or a deployment that stays up
after you close the terminal.

This page uses `reports.py` from the [functions guide](/concepts/functions).

## On your machine

```python
from reports import summarize_sales

summarize_sales.local([1200, 3500, 800])
summarize_sales([1200, 3500, 800])
```

Both run in your Python process. Nothing is uploaded and no task is recorded.
The image, volumes, secrets, GPU, retries, and lifecycle hooks on the decorator
do not apply, so this is for logic that has no remote dependencies, and for
unit tests.

## One remote run

```bash
uv run lazycloud run reports:summarize_sales '[1200, 3500, 800]'
```

```python
summarize_sales.remote([1200, 3500, 800])
```

This builds the image if needed, uploads your source, starts a container with
the decorator's resources, and streams logs and the result. Nothing is
deployed; the container stays up for the function's `keep_warm` window (10
seconds by default) and then stops. The run is recorded as a task you can
revisit with `uv run lazycloud task show <task-id>`.

Use it for a batch job you run by hand, for checking that the image and
secrets are right before deploying, and for GPU work you do not want to keep
warm. The source that ran is the working tree at the moment you called it, so
two runs a minute apart can run different code. Pods have the same shape:
`web.create()` starts one instance from the definition, and
`instance.terminate()` stops it. Sandboxes only run this way.

## A preview that reloads

```bash
uv run lazycloud serve reports:summarize_sales
```

The preview runs the workload on LazyCloud with a temporary URL, keeps its
container warm until you press Ctrl+C, and syncs your working directory into
it as you save. For a function, source edits take effect after in-flight calls
finish. For an endpoint or ASGI app, the server restarts on each change and
the preview URL stays the same.

Calls from the same machine and workspace go to the preview while it runs:

```bash
uv run lazycloud run reports:summarize_sales '[1200, 3500, 800]'
```

```python
summarize_sales.remote([1200, 3500, 800])
```

Both use the preview container instead of starting a new one. A serve preview
is the fastest loop for remote-only code: the image is built once, and each
edit is a file sync rather than a container start.

## A deployment

```bash
uv run lazycloud deploy reports
```

A deployment is durable. Its containers start on demand, scale under the
workload's [autoscaler](/concepts/scaling), and keep running after you close
the terminal. Endpoints get a stable URL, scheduled functions start firing, and
functions become callable from other deployed code and from exported client
packages. Each deploy records a new version; `deployment_version` on a client
pins one.

Deploy when something else calls the code: another service, a schedule, a
teammate, or a function running inside LazyCloud. A remote function that calls
`other.remote()` needs `other` deployed, because a container has no working
tree to upload.

## Where a call goes

`summarize_sales.remote()` and `uv run lazycloud run` resolve the target in this
order:

1. A serve preview for this function, app, and workspace started from this
   machine.
2. Otherwise, from your machine, a fresh run of the working tree.
3. Otherwise, inside a LazyCloud container, the deployed function.

The endpoint client makes the choice explicit. `count_words.request(...)` uses
`target="auto"`, which is the preview when one is running and the deployment
otherwise. `count_words.target("deployed").request(...)` skips the preview,
and `target("served")` fails rather than fall through to the deployment.
`deployment_name` and `deployment_version` pin one deployment.

## Pick one

| You want to | Use |
| --- | --- |
| Check logic or run unit tests | `.local()` |
| Run a job once with the real image, GPU, and secrets | `lazycloud run` or `.remote()` |
| Iterate on remote-only code, or test an endpoint from a browser | `lazycloud serve` |
| Keep a URL, schedule, or callable function up | `lazycloud deploy` |
| Poke at the image or a running container | `lazycloud shell`, `lazycloud dev` |

`uv run lazycloud shell reports:summarize_sales` opens a shell in the
function's image, and `uv run lazycloud dev` opens one with your working
directory synced in. See the [CLI reference](/cli/deploy-and-run) for the flags
each command accepts.
