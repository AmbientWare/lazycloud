title: "Compute"
description: "Where your workloads run: LazyCloud's compute, your own AWS account, or machines you join."

Use LazyCloud compute to run without managing machines. Choose CPU, memory,
and GPUs in your workload definition. You pay while its container runs,
including startup and idle time.

## Request a GPU

Save this as `compute_demo.py`:

```python
import subprocess

from lazycloud import App

app = App("compute_demo")


@app.function(cpu=2.0, memory="4Gi", gpu="l4", gpu_count=1)
def gpu_name() -> str:
    return subprocess.check_output(
        ["nvidia-smi", "--query-gpu=name", "--format=csv,noheader"], text=True
    ).strip()
```

Run `uv run lazycloud run compute_demo:gpu_name` to print the assigned GPU's name.
Check your GPU access and balance in Settings, then Billing first.

Available GPU models are `t4`, `a10g`, `l4`, `l40s`, `a100-40`, `a100-80`,
`h100`, and `h200`. Pass a list to state a preference, best first, and `"any"`
last to take whatever is free.

Check what your workspace is using:

```bash
uv run lazycloud compute status
uv run lazycloud compute instances
uv run lazycloud compute workloads
```

## Where a workload runs

The workspace decides. Every workspace has a location fixed when you create
it: LazyCloud's own compute, or an AWS account you have connected. A workload
runs where its workspace lives, and its volumes are stored there too.

```bash
uv run lazycloud workspace create research            # runs on LazyCloud
uv run lazycloud workspace create research --cloud aws # runs in your AWS account
```

A workspace never changes location. To move work, create a new workspace in
the other location and copy the data across.

The one exception is a machine you joined yourself. A workload names it with
`machine="gpu-1"` on the decorator, or `--machine gpu-1` on `deploy`, `run`,
`serve`, `shell`, or `dev`, and then runs only there. If that machine is
offline, or does not serve the workload's workspace, the workload fails
rather than running somewhere else.

## Your own AWS account

On the Business plan you can connect one AWS account. Workspaces you create
with `--cloud aws` then run there: LazyCloud launches instances inside your
account when a workload needs them and shuts them down when they go idle. The
containers, the instances, and a bucket holding the workspace's volumes all
live in your account. AWS bills you for them, and LazyCloud charges a
management fee based on compute rates. Egress is billed the same as
everywhere else.

```bash
uv run lazycloud cloud connect aws --account-id 123456789012
```

Authorize the connection with your AWS profile. The command submits a
CloudFormation stack that creates the management role and network:

```bash
uv run lazycloud cloud authorize --profile YOUR_AWS_PROFILE
uv run lazycloud cloud status
```

Check the CloudFormation stack's events in your AWS account if authorization
has not completed. After the stack finishes, run `uv run lazycloud cloud validate`,
then `uv run lazycloud cloud status` to read the result. The dashboard shows the same
connection under Settings, then Compute. Once it is ready, create a workspace
in it.

LazyCloud manages instance selection, regions, capacity limits, warm workers,
idle shutdown, and root disks for every workspace in the account. Choose CPU,
memory, and GPU on each workload.

If the authorization stops working, for example after a role change in AWS,
`uv run lazycloud cloud status` says so. `uv run lazycloud cloud reconnect` starts a
replacement authorization, and `uv run lazycloud cloud validate` rechecks the current
one.

`uv run lazycloud cloud disconnect` drains instances and removes the
connection; add `--wait` to block until it is gone. It is refused while any
workspace lives in the account, because those workspaces have nowhere else to
run and their volumes are in your bucket. Delete them first.

## Your own machines

You can join a Linux server you own and run workloads from workspaces you
choose on it. This suits an on-premises GPU box, a bare-metal host, or a VM.
Containers on your own machines are not charged compute; volumes and egress
still are.

The host needs:

- Linux on amd64 or arm64, with systemd and root or sudo access.
- A rootful Docker daemon.
- Outbound DNS and TCP port 443 for HTTPS and authenticated TLS connections.
  No inbound port, port forwarding, or static IP is needed.

Run the join on the machine itself:

```bash
uv run lazycloud machine join --name gpu-1 --workspaces research,staging --gpu a100-80 --max-gpus 4 --max-cpu 32 --max-memory 128Gi
```

The name is unique across your account, and it is what workloads pin to. The
workspaces are the only ones whose workloads may land on the machine. The
command runs the agent in the foreground; add `--background` to install a
service that keeps running after the terminal closes.

Change which workspaces a machine serves at any time:

```bash
uv run lazycloud machine update gpu-1 --workspaces research,staging,prod
uv run lazycloud machine list
```

The dashboard has the same flow under Settings, then Compute, then Join a
machine, and shows the host checks as they pass. Each machine row there lists
the workspaces it serves and lets you edit them.

Run a workload on the machine by naming it:

```python
@app.function(cpu=2.0, memory="4Gi", gpu="a100-80", machine="gpu-1")
def gpu_name() -> str:
    return subprocess.check_output(
        ["nvidia-smi", "--query-gpu=name", "--format=csv,noheader"], text=True
    ).strip()
```

Going offline does not remove a machine, but leaving does, and a workload
pinned to a removed machine fails until a machine joins under that name
again. When retiring a machine, finish its active workloads and remove it
with `uv run lazycloud machine remove <machine-id>`, using the ID from `machine list`.
