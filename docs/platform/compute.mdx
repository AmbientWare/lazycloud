LazyCloud compute runs your workloads with no machines to manage. CPU, memory,
and GPUs come from the workload definition. You pay while its container runs,
including startup and idle time.

## Where a workload runs

The workspace decides. You fix its location when you create it, either
LazyCloud's own compute or an AWS account you have connected. A workload runs
where its workspace lives, and its volumes live there too.

```bash
uv run lazycloud workspace create research            # runs on LazyCloud
uv run lazycloud workspace create research --cloud aws # runs in your AWS account
```

A workspace never changes location. Moving work means creating a workspace in
the other location and copying the data across.

The one exception is a machine you joined yourself. A workload names it with
`machine="gpu-1"` on the decorator and then runs only there. If that machine is
offline, or does not serve the workload's workspace, the workload fails rather
than running somewhere else.

## Check usage

```bash
uv run lazycloud compute status
uv run lazycloud compute instances
uv run lazycloud compute workloads
```

[Resources and options](/concepts/resources) covers sizing a workload and
requesting a GPU.

## Your own AWS account

On the Business plan you can connect one AWS account. Workspaces you create
with `--cloud aws` then run there. LazyCloud launches instances inside your
account when a workload needs them and shuts them down when they go idle. The
containers, the instances, and a bucket holding the workspace's volumes all
live in your account. AWS bills you for them, and LazyCloud charges a
management fee based on compute rates. Egress bills the same as on LazyCloud
compute.

```bash
uv run lazycloud cloud connect aws --account-id 123456789012
```

Authorize the connection with your AWS profile. The command submits a
CloudFormation stack that creates the management role and network:

```bash
uv run lazycloud cloud authorize --profile YOUR_AWS_PROFILE
uv run lazycloud cloud status
```

If authorization has not completed, check the CloudFormation stack's events in
your AWS account. After the stack finishes, run
`uv run lazycloud cloud validate`, then `uv run lazycloud cloud status` to read
the result. The dashboard shows the same connection under Settings, then
Compute. Once it is ready, create a workspace in it.

LazyCloud manages instance selection, regions, capacity limits, warm workers,
idle shutdown, and root disks for every workspace in the account. Each workload
chooses its CPU, memory, and GPU.

If the authorization stops working, for example after a role change in AWS,
`uv run lazycloud cloud status` says so. `uv run lazycloud cloud reconnect`
starts a replacement authorization, and `uv run lazycloud cloud validate`
rechecks the current one.

`uv run lazycloud cloud disconnect` drains instances and removes the
connection. Add `--wait` to block until it is gone. LazyCloud refuses to
disconnect while any workspace lives in the account, because those workspaces
have nowhere else to run and their volumes are in your bucket. Delete them
first.

## Your own machines

A Linux server you own, such as an on-premises GPU box, a bare-metal host, or
a VM, can join your account and run workloads for the workspaces you choose.
Containers on your own machines incur no compute charges. Volumes and egress
still bill.

The host needs:

- Linux on amd64 or arm64, with systemd and root or sudo access.
- A rootful Docker daemon.
- Outbound DNS and TCP port 443 for HTTPS and authenticated TLS connections.
  No inbound port, port forwarding, or static IP is needed.

Run the join on the machine itself:

```bash
uv run lazycloud machine join --name gpu-1 --workspaces research,staging --gpu a100-80 --max-gpus 4 --max-cpu 32 --max-memory 128Gi
```

The name is unique across your account, and workloads pin to it. Only
workloads from the listed workspaces may land on the machine. The command runs
the agent in the foreground. Add `--background` to install a service that
keeps running after the terminal closes.

`machine update` changes which workspaces a machine serves at any time:

```bash
uv run lazycloud machine update gpu-1 --workspaces research,staging,prod
uv run lazycloud machine list
```

The dashboard has the same flow under Settings, then Compute, then Join a
machine, and shows the host checks as they pass. Each machine row there lists
the workspaces it serves and lets you edit them.

A workload that names the machine runs there:

```python
from lazycloud import GpuType


@app.function(cpu=2.0, memory="4Gi", gpu=GpuType.A100_80, machine="gpu-1")
def gpu_name() -> str:
    return subprocess.check_output(
        ["nvidia-smi", "--query-gpu=name", "--format=csv,noheader"], text=True
    ).strip()
```

## What the compute panels show

Settings, then Compute has two panels. The connected cloud card lists the
machines LazyCloud launched in your AWS account, with the instance type,
availability zone and launch time from the provider. The self-hosted panel
lists the machines you joined, by name, with the workspaces each one serves.
A machine appears in exactly one panel, chosen by the placement recorded on
the machine. A node launched in your account never shows up as a self-hosted
machine, and a joined host never counts as cloud capacity. The card's counts
come from the same list as its rows.

Every machine carries one lifecycle phase, and both panels show the same chip:

- `requested`: a join command was issued, or the provider was asked for an
  instance, and nothing has reported yet.
- `provisioning`: the provider reports the instance running, but the node
  has not reported for itself.
- `booting`: the node is installing the agent.
- `joining`: the agent has enrolled and is waiting for its first heartbeat.
- `ready`: the machine takes workloads.
- `draining`: LazyCloud places no new work here, and running work finishes.
- `terminating`: shutdown has been requested at the provider or the host.
- `deleted`: the provider or the host confirmed it is gone. Deleted machines
  leave the list.
- `failed`: the machine did not become ready, or stopped serving long enough
  to count as failed. The chip names the reason.

A machine that stops sending heartbeats stays `ready`. Its row says how long
it has been quiet, and a second badge shows it offline. The same badge shows
draining, cordoned, or at risk when the host's capacity is limited. The panels
update from the workspace change stream as phases change, without polling.

`uv run lazycloud compute instances` prints the connected cloud's machines
with the same phases. `uv run lazycloud machine list` prints the joined ones.

Going offline does not remove a machine, but leaving does. A deployment stays
on the machine it was deployed to. If that machine leaves, the deployment
waits for capacity until a machine joins under that name again and you
redeploy. A run or sandbox resolves the name each time it starts, and fails at
once while the machine is gone.

To retire a machine, finish its active workloads, then run
`uv run lazycloud machine remove <machine-id>` with the ID from `machine list`.
Removing a machine from the account side revokes the host. An agent still
running there stops, and a host that lost its local identity gets its name
back this way.
