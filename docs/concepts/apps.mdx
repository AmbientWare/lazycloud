---
title: "Apps and workloads"
description: "Lay out a project as an app of workloads, keep its configuration in code, and deploy, export, or remove it as a unit."
---

An `App` is a named group of workloads in a workspace. Everything in one app is
deployed, paused, and deleted together, so draw the boundary around code that
ships together: an API and the batch functions it calls, a model server and its
warm-up job.

## Define an app

```python
from lazycloud import App

app = App("text_tools")


@app.function()
def count_words(text: str) -> int:
    return len(text.split())


@app.endpoint(name="count", methods=["POST"])
def count(text: str) -> dict[str, int]:
    return {"words": count_words.local(text)}
```

Each decorator registers a workload with the app. `@app.function`,
`@app.endpoint`, `@app.asgi`, `@app.realtime`, and `app.pod(...)` are deployed
with the app. `app.sandbox(...)` defines containers your code creates on
demand; a deploy never starts them.

App names start with a lowercase letter and contain lowercase letters, digits,
or underscores, up to 63 characters. Workload names default to the Python name
and must be unique per kind within the app.

## Keep configuration in code

The decorator is the whole definition: image, CPU, memory, GPU, volumes, secret
names, schedule, and scaling. Change it in the file and deploy again. CLI flags
such as `--gpu` or `--memory` override a value for one command, which suits an
experiment; the next deploy without the flag goes back to the file.

Values that differ between workspaces or change without a code change belong
elsewhere: credentials in [secrets](/concepts/secrets), files in
[volumes](/concepts/volumes). A volume or secret is shared by name across the
workspace, so two apps that name the same volume read the same files.

## Deploy the app or one workload

```bash
uv run lazycloud deploy text_tools          # every workload in the app
uv run lazycloud deploy text_tools:count    # just the endpoint
```

A module reference deploys its only app. `module:object` selects one workload
or, when a module has several apps, one app. See
[handler references](/cli/overview#handler-references) for the full syntax. From
Python, `app.deploy()` deploys the whole app and `count.deploy()` one workload.

`--diff` shows what a deploy would add, redeploy, or remove without changing
anything. `--prune` removes deployed workloads you deleted from the code;
stored volumes and secrets stay. See [`lazycloud deploy`](/cli/deploy-and-run#lazycloud-deploy).

## Split an app across files

Workloads belong to the `App` object they are registered on, not to the file
that defines them. Import the app into each module and register workloads there:

```python
# text_tools/app.py
from lazycloud import App

app = App("text_tools")
```

```python
# text_tools/api.py
from text_tools.app import app


@app.endpoint(name="count", methods=["POST"])
def count(text: str) -> dict[str, int]:
    return {"words": len(text.split())}
```

If `text_tools/workers.py` registers the batch functions the same way, deploy
both files so the CLI imports every registration:

```bash
uv run lazycloud deploy text_tools/api.py text_tools/workers.py
```

## Call one workload from another

Inside a container, `count_words.remote(...)` calls the deployed `count_words`,
because a container has no working tree to upload. Deploy the whole app before
running a parent that calls its siblings remotely. `.local(...)` runs the
callee in the caller's own process instead, with the caller's image and
resources.

## Call deployed workloads from other projects

```bash
uv run lazycloud app export text_tools
```

This writes a typed Python package to `lazycloud_clients/text_tools`, so
another project can call the deployed functions and endpoints without importing
your source. Functions get `remote()` and `async_remote()`; endpoints get
`request()` and `async_request()`. Callers sign in with `lazycloud login`; the
package holds deployment references and schemas, never credentials.

ASGI routes are typed from the app's OpenAPI schema at `/openapi.json`, with
methods named after operation IDs. Point elsewhere when needed:

```bash
uv run lazycloud app export web_app --openapi-path service=/schema/openapi.json
uv run lazycloud app export web_app --openapi service=./openapi.json
```

Routes the generator cannot type fail with an explanation, and an ASGI app with
no schema keeps raw `request()`. Pods and sandboxes are not exported. Export
again after deploying a contract change.

## Manage a deployed app

```bash
uv run lazycloud app show text_tools
uv run lazycloud app pause text_tools     # stop every workload, keep definitions
uv run lazycloud app resume text_tools
uv run lazycloud app delete text_tools
```

Deleting an app or a workload never deletes the volumes, secrets, or other
stored data it used. Remove those separately once you no longer need them.
