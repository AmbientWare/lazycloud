---
title: "Apps and workloads"
description: "Lay out a project as an app of workloads, keep its configuration in code, and deploy it as a unit."
---

An `App` is a named group of workloads in a workspace. You deploy, pause, and
delete an app as one unit, so its boundary fits code that ships together, such
as an API and the batch functions it calls, or a model server and its warm-up
job.

## Define an app

```python
from lazycloud import App

app = App("text_tools")


@app.function()
def count_words(text: str) -> int:
    return len(text.split())


@app.endpoint(name="count", methods=["POST"])
def count(text: str) -> dict[str, int]:
    return {"words": count_words.local(text)}
```

Each decorator registers a workload with the app. `@app.function`,
`@app.endpoint`, `@app.asgi`, `@app.realtime`, and `app.pod(...)` deploy with
the app. `app.sandbox(...)` defines containers your code creates on demand, and
a deploy never starts them.

App names start with a lowercase letter and contain lowercase letters, digits,
or underscores, up to 63 characters. Workload names default to the Python name
and must be unique per kind within the app.

## Keep configuration in code

The decorator is the whole definition: image, CPU, memory, GPU, volumes, secret
names, schedule, and scaling. No CLI flag or SDK call overrides it, so a deploy
runs exactly what the file says. A change means editing the file and deploying
again.

Values that differ between workspaces or change without a code change belong
outside the decorator. Credentials go in [secrets](/concepts/secrets) and files
in [volumes](/concepts/volumes). The workspace shares volumes and secrets by
name, so two apps that name the same volume read the same files.

## Deploy the app or one workload

```bash
uv run lazycloud deploy text_tools          # every workload in the app
uv run lazycloud deploy text_tools:count    # just the endpoint
```

A module reference deploys the module's only app. `module:object` selects one
workload or, when a module has several apps, one app. See [handler
references](/cli/overview#handler-references) for the full syntax. From Python,
`app.deploy()` deploys the whole app and `count.deploy()` one workload.

## Split an app across files

A workload belongs to the `App` object that registers it, not to the file that
defines it. Each module imports the app and registers its workloads:

```python
# text_tools/app.py
from lazycloud import App

app = App("text_tools")
```

```python
# text_tools/api.py
from text_tools.app import app


@app.endpoint(name="count", methods=["POST"])
def count(text: str) -> dict[str, int]:
    return {"words": len(text.split())}
```

If `text_tools/workers.py` registers the batch functions the same way, the
deploy names both files so the CLI imports every registration:

```bash
uv run lazycloud deploy text_tools/api.py text_tools/workers.py
```

## Call one workload from another

Inside a container, `count_words.remote(...)` calls the deployed `count_words`,
because a container has no working tree to upload. A parent that calls its
siblings remotely therefore needs the whole app deployed. `.local(...)` instead
runs the callee in the caller's own process, with the caller's image and
resources.

## Call deployed workloads from other projects

```bash
uv run lazycloud app export text_tools
```

This writes a typed Python package to `lazycloud_clients/text_tools`, so
another project can call the deployed functions and endpoints without importing
your source. Functions get `remote()` and `async_remote()`. Endpoints get
`request()` and `async_request()`. Callers sign in with `lazycloud login`, and
the package holds deployment references and schemas, never credentials.

The generator types ASGI routes from the app's OpenAPI schema at `/openapi.json`
and names methods after operation IDs. To read the schema from another path or
a local file:

```bash
uv run lazycloud app export web_app --openapi-path service=/schema/openapi.json
uv run lazycloud app export web_app --openapi service=./openapi.json
```

Routes the generator cannot type fail with an explanation. An ASGI app with no
schema keeps raw `request()`. Export skips pods and sandboxes. A contract change
needs a fresh export once it deploys.

## Remove a workload

Deleting it from the code and deploying with `--prune` removes it. See
[`lazycloud deploy`](/cli/deploy-and-run#lazycloud-deploy). Removing a workload
or deleting an app never deletes the volumes and secrets it used.
