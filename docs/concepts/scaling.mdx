---
title: "Scaling and concurrency"
description: "How many containers a workload runs, how much each one handles at once, and what happens when work arrives faster than that."
---

Capacity is containers multiplied by what one container does at once. Both
numbers are settings on the decorator, and both default to one. A function
with no scaling settings serves one call at a time in one container, and a
`.map()` over 500 inputs runs them one after another. This page covers the
settings that change that, what they default to for each workload kind, and
how they interact.

## Defaults

| | Function | Endpoint | ASGI and realtime | Pod | Sandbox |
| --- | --- | --- | --- | --- | --- |
| `cpu` | `0.125` | `1.0` | `1.0` | `1.0` | `1.0` |
| `memory` | `"128Mi"` | `"128Mi"` | `"128Mi"` | `"128Mi"` | `128` MiB |
| `timeout_seconds` | `3600` per call | `180` per request | `180` per request | | |
| `retries` | `3` | `0` | | | |
| Idle window | `keep_warm=10` | `keep_warm=180` | `keep_warm_seconds=180` | `keep_warm=600` | `keep_warm_seconds=600` |
| Per container | `concurrency=1` | `workers=1`, `concurrency=1` | `workers=1`, `concurrent_requests=1` | one process | |
| Containers | at most 1 | at most 1 | at most 1 | 1 | 1 per `create()` |
| Queue limit | `max_pending_tasks=100` | `max_pending_tasks=100` | `max_pending_tasks=100` | | |

Every container gets 100 GiB of scratch disk; set `disk="20Gi"` to reserve a
different amount. Scheduled functions default to `keep_warm=0` because the next
run is minutes or hours away.

## Concurrency inside one container

### Functions

`concurrency` is how many calls one container serves at once. Each call gets
its own process unless you set `in_process=True`, which runs them as threads
in one interpreter:

```python
from lazycloud import App

app = App("inference")


@app.function(gpu="l4", memory="8Gi", concurrency=4, in_process=True)
def classify(image_bytes: bytes) -> str:
    ...
```

Separate processes are the right default for CPU-bound work: they run in
parallel and a crash in one does not take down the others. Each process runs
`on_start` and holds its own copy of whatever that loads. `in_process=True`
is for a model or client that is expensive to load. Loaded once in `on_start`,
it serves every slot. The cost is the GIL: pure-Python CPU work in those
threads runs one at a time, so this pays off when the handler spends its time
in a GPU kernel, a network call, or a C extension. Cancelling a call in a
shared interpreter stops the container, and the other calls in it retry.

### Endpoints and ASGI apps

`workers` is the number of server processes in one container. `concurrency`
(`concurrent_requests` for ASGI and realtime) is how many requests each process
handles at once. The container accepts `workers * concurrency` requests in
flight.

```python
@app.endpoint(cpu=2, memory="1Gi", workers=2, concurrency=16)
def lookup(key: str) -> dict[str, str]:
    ...
```

Workers are separate processes, so they do not share memory. A model loaded in
`on_start` is loaded once per worker. For a GPU model, keep `workers=1` and
raise `concurrency`. For a CPU-bound handler, set `workers` to the number of
CPUs and `concurrency` to one or two, since more requests per process only
queue behind the GIL. Async handlers and I/O-bound code can take a high
`concurrency` in one worker.

## More containers

`QueueDepthAutoscaler` sets how many containers a workload may run and how much
work each is expected to carry:

```python
from lazycloud import App, QueueDepthAutoscaler

app = App("etl")


@app.function(
    cpu=2,
    memory="2Gi",
    concurrency=4,
    max_pending_tasks=1000,
    autoscaler=QueueDepthAutoscaler(
        min_containers=0,
        max_containers=20,
        tasks_per_container=4,
    ),
)
def transform(path: str) -> int:
    ...
```

`max_containers` is the ceiling. `tasks_per_container` is how many queued
calls justify one container: the autoscaler starts
`ceil(queued / tasks_per_container)` containers, up to the ceiling. Set it to
the container's real concurrency, `concurrency` for a function or
`workers * concurrency` for an endpoint. Setting it lower starts containers
that sit half empty; setting it higher queues calls that a new container could
have taken.

When you omit `autoscaler`, the workload gets `max_containers=1` and a
`tasks_per_container` equal to its per-container concurrency. When you supply
one, `tasks_per_container` defaults to `1`, so set it.

Functions scale on queued calls and endpoints scale on requests in flight,
including requests waiting for a container. With `max_containers=20` and
`tasks_per_container=4`, the `transform` function above runs 500 inputs from
`.map()` on 20 containers, 4 at a time each, and releases them 10 seconds
after the queue drains.

Pods scale by hand. `uv run lazycloud deployment scale web --containers 3`
pins a pod deployment to three containers; see [Pods](/concepts/pods).

## Warm containers

A container that has finished its work stays up for the idle window, `keep_warm`
seconds, so the next call skips the start. Startup includes pulling the image,
mounting volumes, and running `on_start`, which for a model server can be a
minute. The defaults assume a function's next call may never come (10 seconds)
and an API's will (180). Raise the window when starts are expensive and calls
are spaced out; set `keep_warm=0` to stop each container as soon as it is
idle. Warm containers are billed while they run.

`min_containers` on the autoscaler keeps that many containers running with no
work at all, so the first call after a quiet hour is served immediately:

```python
@app.endpoint(
    gpu="l4",
    memory="16Gi",
    concurrency=8,
    keep_warm=600,
    autoscaler=QueueDepthAutoscaler(min_containers=1, max_containers=4, tasks_per_container=8),
)
def generate(prompt: str) -> dict[str, str]:
    ...
```

For a function, a floor also disables the idle window: a container that
retired itself could not be part of a count that is supposed to persist, so
only the autoscaler removes containers below the floor. An endpoint container
stops after `keep_warm` seconds with no requests, but never below
`min_containers`.

`checkpoint_enabled=True` on an endpoint snapshots a worker after it has warmed
up, and replacement containers restore from the snapshot instead of running
startup again.

## When the queue is full

`max_pending_tasks` caps calls in flight, queued and running, per workload.
Past the cap a function call fails immediately with a capacity error naming the
limit, and an endpoint returns `429`. The default is 100, and `.map()` submits
every input before the first one finishes, so a batch of 500 needs
`max_pending_tasks=500` or more on the decorator. Raise the cap for bursts you
expect to drain, or leave it and treat the error as backpressure in the caller.

A queued function call stays pending until a container claims it, and
`.remote()` gives up waiting after the function's `timeout_seconds`. An
endpoint request that finds no free slot waits up to `timeout_seconds` (180 by
default) for one, then fails.

A call pending for more than five seconds shows why in the live progress of
`lazycloud run` and in the dashboard: compute starting, the container
starting, every container busy, or the workspace at its compute limit.
`lazycloud.progress()` delivers the same reason to your own code; see
[Understand a pending call](/concepts/functions#understand-a-pending-call).

## Sizing a container

`cpu` and `memory` are reservations. The scheduler places a container on a
machine with that much free, and under pressure the container keeps what it
reserved. When the machine has more to spare the container may use it, up to a
ceiling above the reservation. Pass a pair to set that ceiling yourself:

```python
@app.function(cpu=(1, 4), memory=("2Gi", "8Gi"))
def render(scene: dict[str, float]) -> bytes:
    ...
```

This reserves 1 CPU and 2 GiB, throttles the container at 4 CPUs, and kills it
above 8 GiB. Reservations decide how many containers fit on a machine, so a
smaller reservation places faster and packs tighter; the ceiling protects the
machine from a runaway container.

`gpu` takes a model or an ordered preference. `gpu=["h100", "a100-80", "l4"]`
takes the first model with free capacity. `gpu_count` adds GPUs to one
container. GPU models and prices are on the [Compute](/platform/compute) page.

Workloads run on preemptible capacity by default. A preempted function call
retries under its retry policy, and a preempted endpoint container is replaced.
Set `preemptible=False` for work that cannot tolerate that; it adds the
premium shown on the [pricing page](https://lazycloud.dev/pricing).

## Patterns

### Batch over many inputs

Size the container for one input, then set the autoscaler for the batch.
Failed inputs return `None` from `.map()`; use `spawn_map()` when every input
must succeed before you use the results. See
[Process several inputs](/concepts/functions#process-several-inputs).

```python
@app.function(
    cpu=1,
    memory="1Gi",
    timeout_seconds=600,
    retries=2,
    max_pending_tasks=5000,
    autoscaler=QueueDepthAutoscaler(max_containers=50, tasks_per_container=1),
)
def process_page(url: str) -> int:
    ...


results = list(process_page.map([(url,) for url in urls]))
```

One call per container and 50 containers keeps each call isolated; a crash or
an out-of-memory kill costs one input, not the batch. `max_pending_tasks` is
raised because `.map()` submits the whole batch up front.

### GPU model served over HTTP

One model per container, many requests per model, one container always warm:

```python
MODEL = {}


def load_model() -> None:
    MODEL["embedder"] = ...  # load weights once per worker process


@app.endpoint(
    gpu="a10g",
    memory="16Gi",
    workers=1,
    concurrency=8,
    keep_warm=900,
    timeout_seconds=120,
    on_start=load_model,
    autoscaler=QueueDepthAutoscaler(min_containers=1, max_containers=6, tasks_per_container=8),
)
def embed(texts: list[str]) -> list[list[float]]:
    ...
```

`workers=1` loads the model once. `concurrency=8` lets the handler batch
requests on the GPU. The floor of one absorbs the model load time for the
first request of the day, and five more containers cover bursts.

### CPU API with steady traffic

```python
service = app.asgi(
    name="api",
    cpu=4,
    memory="2Gi",
    workers=4,
    concurrent_requests=32,
    keep_warm_seconds=300,
    autoscaler=QueueDepthAutoscaler(max_containers=10, tasks_per_container=128),
)(fastapi_app)
```

Four workers on four CPUs, 32 async requests each, and a new container for
every 128 requests in flight.

### Long-running job

```python
@app.function(cpu=4, memory="16Gi", timeout_seconds=6 * 3600, retries=0, preemptible=False)
def train(config: dict[str, float]) -> str:
    ...
```

A six hour timeout, no retries because a restarted training run would repeat
six hours of work, and non-preemptible capacity so the machine is not
reclaimed under it. Write checkpoints to a [volume](/concepts/volumes) so a
failure can resume.
