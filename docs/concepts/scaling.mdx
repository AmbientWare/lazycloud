Capacity is containers multiplied by what one container does at once. Both
default to one. A workload with no scaling settings serves one call at a time
in one container, so a `.map()` over 500 inputs runs them one after another.
The per-kind defaults are in
[Resources and options](/concepts/resources#defaults).

## Concurrency inside one container

### Functions

`concurrency` is how many calls one container serves at once. Each call gets
its own process unless you set `in_process=True`, which runs them as threads
in one interpreter:

```python
from lazycloud import App, GpuType

app = App("inference")


@app.function(gpu=GpuType.L4, memory="8Gi", concurrency=4, in_process=True)
def classify(image_bytes: bytes) -> str:
    ...
```

Separate processes suit CPU-bound work. They run in parallel, and a crash in
one does not take down the others. Each process runs `on_start` and holds its
own copy of whatever that loads. `in_process=True` suits a model or client that
is expensive to load. `on_start` loads it once, and every slot shares it. The
cost is the GIL. Pure-Python CPU work in those threads runs one at a time, so
this pays off only when the handler spends its time in a GPU kernel, a network
call, or a C extension. Cancelling a call in a
shared interpreter stops the container, and the other calls in it retry.

### Endpoints and ASGI apps

`workers` is the number of server processes in one container. `concurrency`
is how many requests each process handles at once, and ASGI and realtime call
it `concurrent_requests`. The container accepts `workers * concurrency`
requests in flight.

```python
@app.endpoint(cpu=2, memory="1Gi", workers=2, concurrency=16)
def lookup(key: str) -> dict[str, str]:
    ...
```

Workers are separate processes, so they do not share memory. `on_start` runs in
each worker, so each one loads its own copy of the model. A GPU model suits
`workers=1` with a higher `concurrency`. A CPU-bound handler suits `workers`
equal to the CPU count and a `concurrency` of one or two, since more requests
per process only queue behind the GIL. Async handlers and I/O-bound code can
take a high `concurrency` in one worker.

## More containers

`QueueDepthAutoscaler` sets how many containers a workload may run and how much
work each is expected to carry:

```python
from lazycloud import App, QueueDepthAutoscaler

app = App("etl")


@app.function(
    cpu=2,
    memory="2Gi",
    concurrency=4,
    max_pending_tasks=1000,
    autoscaler=QueueDepthAutoscaler(
        min_containers=0,
        max_containers=20,
        tasks_per_container=4,
    ),
)
def transform(path: str) -> int:
    ...
```

`max_containers` is the ceiling. `tasks_per_container` is how many queued
calls justify one container. The autoscaler starts
`ceil(queued / tasks_per_container)` containers, up to the ceiling. It fits best
at the container's real concurrency, `concurrency` for a function or
`workers * concurrency` for an endpoint. A lower value starts containers that
sit half empty. A higher value queues calls that a new container could have
taken.

When you omit `autoscaler`, the workload gets `max_containers=1` and a
`tasks_per_container` equal to its per-container concurrency. When you supply
one, `tasks_per_container` defaults to `1` rather than that concurrency.

Functions scale on queued calls and endpoints scale on requests in flight,
including requests waiting for a container. With `max_containers=20` and
`tasks_per_container=4`, the `transform` function above runs 500 inputs from
`.map()` on 20 containers, 4 at a time each, and releases them 10 seconds
after the queue drains.

Pods scale by hand. `uv run lazycloud deployment scale web --containers 3`
pins a pod deployment to three containers. See [Pods](/concepts/pods).

## Warm containers

A container that has finished its work stays up for the idle window, `keep_warm`
seconds, so the next call skips the start. A start pulls the image, mounts
volumes, and runs `on_start`, which can take a minute for a model server. The
function default of 10 seconds assumes the next call may never come. The
endpoint default of 180 assumes it will. A longer window suits expensive starts
and spaced-out calls. `keep_warm=0` stops each container as soon as it is idle.
You pay for warm containers while they run, so an idle window is a trade of
money for start time. Scheduled functions default to `keep_warm=0`, because a
container kept warm between runs minutes or hours apart costs money and saves
nothing. [Pods](/concepts/pods#deploy-it) also accept `keep_warm=-1`, which
keeps one container up until you stop the deployment.

`min_containers` on the autoscaler keeps that many containers running with no
work at all, so the first call after a quiet hour does not wait for a start:

```python
@app.endpoint(
    gpu=GpuType.L4,
    memory="16Gi",
    concurrency=8,
    keep_warm=600,
    autoscaler=QueueDepthAutoscaler(min_containers=1, max_containers=4, tasks_per_container=8),
)
def generate(prompt: str) -> dict[str, str]:
    ...
```

For a function, a floor also disables the idle window. Idle containers do not
stop on their own, and only the autoscaler removes them. An endpoint container
stops after `keep_warm` seconds with no requests, but never below
`min_containers`.

## When the queue is full

`max_pending_tasks` caps calls in flight, queued and running, per workload.
Past the cap a function call fails immediately with a capacity error naming the
limit, and an endpoint returns `429`. The default is 100. `.map()` submits
every input before the first one finishes, so a batch of 500 needs
`max_pending_tasks=500` or more on the decorator. A higher cap suits bursts you
expect to drain. Otherwise the error works as backpressure in the caller.

A queued function call stays pending until a container claims it, and
`.remote()` gives up waiting after the function's `timeout_seconds`. An
endpoint request that finds no free slot waits up to `timeout_seconds`, 180 by
default, for one and then fails.

After a call has been pending for five seconds, the CLI and dashboard show why.
See [pending tasks](/concepts/tasks-and-logs#why-a-task-is-pending).

## Patterns

### Batch over many inputs

The container is sized for one input and the autoscaler for the batch. Failed
inputs return `None` from `.map()`, and `spawn_map()` suits a batch where every
input must succeed before you use the results. See
[Process a batch](/concepts/functions#process-a-batch).

```python
@app.function(
    cpu=1,
    memory="1Gi",
    timeout_seconds=600,
    retries=2,
    max_pending_tasks=5000,
    autoscaler=QueueDepthAutoscaler(max_containers=50, tasks_per_container=1),
)
def process_page(url: str) -> int:
    ...


results = list(process_page.map([(url,) for url in urls]))
```

One call per container across 50 containers keeps each call isolated, so a
crash or an out-of-memory kill costs one input, not the batch.
`max_pending_tasks=5000` makes room for `.map()` to submit the whole batch up
front.

### GPU model served over HTTP

One model per container, many requests per model, one container always warm:

```python
MODEL = {}


def load_model() -> None:
    MODEL["embedder"] = ...  # load weights once per worker process


@app.endpoint(
    gpu=GpuType.A10G,
    memory="16Gi",
    workers=1,
    concurrency=8,
    keep_warm=900,
    timeout_seconds=120,
    on_start=load_model,
    autoscaler=QueueDepthAutoscaler(min_containers=1, max_containers=6, tasks_per_container=8),
)
def embed(texts: list[str]) -> list[list[float]]:
    ...
```

`workers=1` loads the model once. `concurrency=8` lets the handler batch
requests on the GPU. The floor of one keeps a loaded model ready for the first
request of the day, and five more containers cover bursts.

### CPU API with steady traffic

```python
service = app.asgi(
    name="api",
    cpu=4,
    memory="2Gi",
    workers=4,
    concurrent_requests=32,
    keep_warm_seconds=300,
    autoscaler=QueueDepthAutoscaler(max_containers=10, tasks_per_container=128),
)(fastapi_app)
```

Four workers on four CPUs, 32 async requests each, and a new container for
every 128 requests in flight.

### Long-running job

```python
@app.function(cpu=4, memory="16Gi", timeout_seconds=6 * 3600, retries=0, preemptible=False)
def train(config: dict[str, float]) -> str:
    ...
```

The timeout is six hours. `retries=0` prevents a restart that would repeat the
work already done, and `preemptible=False` keeps the machine from being
reclaimed mid-run. Checkpoints written to a [volume](/concepts/volumes) let a
new run resume after a failure.
