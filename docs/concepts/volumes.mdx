A volume keeps files after your container stops. Declare it in Python and
attach it to each workload that needs it. LazyCloud creates a missing volume
when preparing the first container's mounts and reuses it on later runs.

## Declare and use a volume

Save this as `reports.py`:

```python
import json
from pathlib import Path

from lazycloud import App, Volume

app = App("reports")
reports = Volume("sales-reports", "/reports")


@app.function(volumes=[reports])
def save_report(amounts_cents: list[int]) -> dict[str, int]:
    summary = {"sales": len(amounts_cents), "total_cents": sum(amounts_cents)}
    Path("/reports/latest.json").write_text(json.dumps(summary))
    return summary


if __name__ == "__main__":
    print(save_report.remote([1200, 3500, 800]))
    reports.get("latest.json", "latest.json")
```

Run it with the SDK installed and signed in:

```bash
uv run python reports.py
```

The function returns three sales totaling 5500 cents. The script downloads
`latest.json` to your current directory. No separate volume-creation command
is needed. Repeating the run replaces that file.

`Volume(...)` declares the name and mount path; constructing the object alone
makes no API call. Attaching it with `volumes=[reports]` tells LazyCloud to
mount it. The same name in the same workspace refers to the same stored files,
even when used by another app. Choose a different name for separate data.

Changing the mount path changes where a container sees the files. Changing the
volume name selects another volume; it does not move or delete the old data.
Removing a mount or deleting a deployment also leaves stored files intact.

Volume storage is billed per GiB-month. See [Plans and limits](/platform/plans).

## Where volumes live

A volume is stored in its workspace's bucket, and that bucket is wherever the
workspace was created: LazyCloud storage, or your connected AWS account when
the workspace was created with `--cloud aws`. That location never changes. To
move data to a workspace in another location, create the new workspace and
copy the files with `lazycloud cp`.

Volumes in a workspace that lives in your AWS account are billed by AWS, not
by LazyCloud. See [Compute](/platform/compute) for how workspaces choose a
location.

## Upload inputs before the first run

If a workload needs files before it starts, create or reuse its declared
volume from your local setup script, then upload them:

```python
from lazycloud import Volume

models = Volume("models", "/models")
models.create()
models.put("weights.pt", "weights.pt")
```

This needs a local `weights.pt`. Attach the same `models` object to your
function with `volumes=[models]` to read `/models/weights.pt` remotely.
`create()` returns the existing volume when its name already exists.
`get_or_create()` performs the same operation and returns a boolean.

Keep provisioning and uploads in an explicit setup function or an
`if __name__ == "__main__":` block. Workload imports should declare resources
without uploading data or changing stored values.

## Read and write from Python

Inside a container, a mounted volume is a directory. From your local script,
use the `Volume` object:

```python
from reports import reports

print(reports.read_text("latest.json"))
print(reports.list())
print(reports.stat("latest.json"))
reports.get("latest.json", "downloaded-report.json")
```

`put(source, destination)` uploads a local file or directory.
`write_text()` and `write_bytes()` write content directly.
`read_text()` and `read_bytes()` retrieve it.
`list_path()` returns entries with size and time, and `move()` renames a path.

For multi-gigabyte uploads, `presigned_url(...)`,
`create_multipart_upload(...)`, `complete_multipart_upload(...)`, and
`abort_multipart_upload(...)` let you upload in parts.

## Share files between containers

Every container that mounts a volume sees the same files, so a volume is how
parallel calls and long-lived services share data. A volume is object storage
presented as a directory, and that shapes what works well:

- A file becomes visible to other containers when the writer closes it, and it
  is durable at that point. Write whole files and close them; do not rely on
  another container seeing a partially written file.
- Two containers writing the same path do not merge; the last close wins.
  Give each call its own output path, such as `/reports/{task_id}.json`, and
  have a final step combine them.
- There are no file locks. Coordinate through a [queue or map](/concepts/queues-maps)
  when containers must take turns.
- Appending to a large file or seeking inside one rewrites the object. Keep
  logs and append-only data in many small files or send them elsewhere.
- The first read of a large file downloads it; later reads on the same machine
  come from a local cache. Large read-mostly data such as model weights is what
  volumes do best.

Download weights once and let every container reuse them:

```python
from pathlib import Path

from lazycloud import App, Volume

app = App("inference")
models = Volume("models", "/models")
WEIGHTS = Path("/models/encoder.safetensors")


def ensure_weights() -> None:
    if WEIGHTS.exists():
        return
    partial = WEIGHTS.with_suffix(".part")
    download_weights(partial)   # your download code
    partial.rename(WEIGHTS)


@app.function(gpu="l4", volumes=[models], on_start=ensure_weights, concurrency=4, in_process=True)
def encode(text: str) -> list[float]:
    ...
```

The `on_start` hook runs before the container takes calls. Downloading to a
`.part` path and renaming means a container that starts mid-download sees
either no file or a complete one. Two containers starting at the same moment
may both download; the rename makes that a wasted download rather than a
corrupt file.

## Ad hoc file operations

Use the CLI to inspect or copy files outside your workflow:

```bash
uv run lazycloud ls sales-reports
uv run lazycloud cp lazycloud://sales-reports/latest.json ./latest.json
```

Paths use `lazycloud://<volume>/<path>`. The scheme is optional except on
the source of a download, where it marks the path as remote. See
[storage commands](/cli/storage) for standalone volume creation and file commands.

## Mount an existing cloud bucket

`CloudBucket` mounts an S3-compatible bucket you own. Reads and writes go
to the bucket in place; nothing is copied into LazyCloud storage.

```python
from pathlib import Path

from lazycloud import App, CloudBucket, CloudBucketConfig

app = App("etl")
bucket = CloudBucket(
    "my-data-bucket",
    "/data",
    CloudBucketConfig(
        access_key="MY_BUCKET_ACCESS_KEY",
        secret_key="MY_BUCKET_SECRET_KEY",
        region="us-east-1",
    ),
)


@app.function(volumes=[bucket])
def read_text_file(key: str) -> str:
    return (Path("/data") / key).read_text()
```

`access_key` and `secret_key` name [workspace secrets](/concepts/secrets).
Provision their values before running the workload. Set both names or neither.
With neither, the mount uses the compute's credentials, such as the instance role
on your [connected AWS account](/platform/compute).

`CloudBucketConfig` also accepts `bucket` when the bucket name differs from the
mount name, `prefix` to mount part of the bucket, `endpoint` for another
S3-compatible store, `force_path_style`, and `read_only`.

The bucket must already exist; declaring a mount never creates it. See
[parallel Parquet processing](/examples/parallel-parquet-s3) for a complete workflow.

## Delete stored data deliberately

After saving a local copy, remove an individual report with
`reports.remove("latest.json")`. `reports.delete()` deletes the whole volume
and every file in it.

For one-off cleanup, inspect the target before deleting:

```bash
uv run lazycloud ls sales-reports
uv run lazycloud rm sales-reports/latest.json
```

Use `uv run lazycloud volume delete sales-reports` only when you no longer need
any of its files. Stop workloads that use the volume first; another invocation
can create an empty volume with the same name.
