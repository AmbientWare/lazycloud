---
title: "Tasks and logs"
description: "Every invocation is a durable task with status, result, and logs."
---

Every function call, endpoint request, queue submission, and scheduled run is
recorded as a durable **task**. Tasks carry status, timing, the serialized
result or error, retry history, and logs.

## Task lifecycle

A task moves through pending, running, and a terminal state: complete, error
(after exhausting retries), cancelled, or timed out. Retries are recorded on
the same task.

## Inspecting tasks from the CLI

```bash
lazycloud task list                 # recent tasks in the workspace
lazycloud task show <task-id>       # status, timing, deployment, container
lazycloud task result <task-id>     # waits for and prints the result
lazycloud task logs <task-id>       # recent log lines for the task
lazycloud task stop <task-id> ...   # stop running tasks
lazycloud task cancel <task-id>     # cancel a pending task
```

`task result` waits by default; use `--no-wait` for a snapshot or `--timeout`
to bound the wait.

## Streaming logs

`lazycloud logs` streams logs by task, container, deployment, or stub:

```bash
lazycloud logs --task-id <task-id> --follow
lazycloud logs --deployment-id <deployment-id> -n 500 --show-timestamp
lazycloud logs --container-id <container-id>
```

Anything your code prints to stdout/stderr is captured. Print with
`flush=True` (or run Python unbuffered) so lines appear promptly.

## Task handles in Python

Spawned functions and queue submissions return handles:

```python
handle = my_function.spawn(42)          # FunctionCall
print(handle.task_id)

queued = my_queue_fn.target("deployed").put(42)
result = queued.result(wait=True, timeout_seconds=120)
print(result.ok, result.status, result.value, result.error)
```

The `Client` session object offers the same workflow when you need task
control outside a decorated object:

```python
from lazycloud import Client

client = Client()
task = client.task_handle("<task-id>")
outcome = task.wait(timeout_seconds=120)
```

Results expose `ok`, `status`, `value`, and `error`. Failed tasks keep the
error message and full logs for debugging.

## Callbacks

Every workload accepts `callback_url`; the platform calls the webhook with
execution events as tasks change state, so external systems can react without
polling.
