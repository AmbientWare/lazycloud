---
title: "Secrets"
description: "Declare credential dependencies in code and provision their values outside source control."
---

Name the secrets a workload needs in its Python definition. Provision their
values in your workspace before deploying or running it. LazyCloud injects
the selected secrets as environment variables.

## Declare a credential dependency

Save this as `service.py`:

```python
import os
import urllib.request

from lazycloud import App, Secret

app = App("service_client")
api_key = Secret("SERVICE_API_KEY")


@app.function(secrets=[api_key.name], retries=0)
def fetch_status(url: str) -> str:
    request = urllib.request.Request(
        url,
        headers={"Authorization": f"Bearer {os.environ[api_key.name]}"},
    )
    with urllib.request.urlopen(request, timeout=30) as response:
        return response.read().decode("utf-8")
```

`Secret("SERVICE_API_KEY")` names the resource; it does not create a value.
Only workloads that list the name receive it. Keep names in source control
and values in your local environment, CI secret store, or a masked prompt.

## Provision the value from Python

Save this as `configure_secrets.py` beside `service.py`:

```python
from getpass import getpass

from service import api_key


if __name__ == "__main__":
    api_key.set(getpass("Service API key: "))
```

Run it once to store the key:

```bash
uv run python configure_secrets.py
```

`set()` creates or replaces the value. Running this setup again updates the
credential. The main guard keeps setup out of workload imports.
For CI, use `api_key.set(os.environ["SERVICE_API_KEY"])` in the setup script
with the value supplied by your CI secret store.

Set `SERVICE_URL` to your service's HTTPS API URL, then call it:

```bash
uv run lazycloud run service:fetch_status "$SERVICE_URL"
```

Secrets are encrypted at rest and scoped to the workspace. Your code can
still expose one by printing it or including it in a response. Setup scripts
should discard the record returned by `set()`, which contains the value.

## Rotate or remove a secret

Run the setup script with the replacement value, then redeploy workloads so
new containers receive it. `create(value)` refuses to replace an existing
secret; use it when accidental rotation would invalidate stored data or tokens.
`update(value)` replaces an existing secret, `get()` reads it, and
`delete()` removes it.

Removing a secret name from a workload does not delete the stored secret.
Delete it explicitly when no workload needs it.

For build-time credentials use `Image.with_secrets([...])`. For
[bucket mounts](/concepts/volumes#mount-an-existing-cloud-bucket), configure
the names of the secrets holding the access key and secret key.

## Ad hoc CLI and dashboard operations

Use the CLI to inspect a secret's metadata:

```bash
uv run lazycloud secret show SERVICE_API_KEY
```

`--reveal` prints the value. Keep it out of shared terminal recordings and logs.
For a one-off update, read the replacement without putting it in shell history:

```bash
read -rsp "New API key: " SERVICE_API_KEY; echo
uv run lazycloud secret modify SERVICE_API_KEY "$SERVICE_API_KEY"
unset SERVICE_API_KEY
```

See [storage commands](/cli/storage) for creation and deletion. The dashboard
also manages secrets under Storage.
