[Develop, test, deploy](/concepts/workflow) explains when each command fits and
where calls go. None of these commands override a workload's configuration,
which comes only from its decorator or constructor.

## lazycloud deploy

```bash
uv run lazycloud deploy HANDLER [HANDLER ...] [options]
```

Deploys one workload or a whole app. See
[handler references](/cli/overview#handler-references) for how `HANDLER`
selects them:

```bash
uv run lazycloud deploy quickstart           # the module's only app
uv run lazycloud deploy myproject.api:app    # one app in a module
uv run lazycloud deploy quickstart:hello     # one workload
```

The deployment name is the workload's `name=` in code. `--source-root <dir>`
packages a different directory as the code root.

With `--json`, a successful app deployment returns one object with the app
name and its resource results. If a deployment fails, the command stops and
leaves already deployed resources in place.

```bash
uv run lazycloud deploy page_stats/api.py --diff
uv run lazycloud deploy page_stats/api.py --diff --prune
uv run lazycloud deploy page_stats/api.py -p
```

Several references deploy their combined definitions, which suits separate
apps deployed together. Each must select a complete app, and references to the
same app object count once. The CLI rejects two definitions that share an app,
workload kind, and name.

`--diff` lists which workloads the deploy would add or redeploy, and marks
deployed workloads the definitions omit as `retain`. It does not compare
source or configuration. Existing workloads show `redeploy` because every
deploy creates another version. `--diff` uploads no source,
builds no images, and changes nothing remotely. It still imports your Python
modules, so their module-level code runs.

`--prune`, or `-p`, removes deployed workloads that the supplied app
definitions omit, and `--diff` shows them as `remove` actions. See
[Remove workloads](/concepts/apps#remove-workloads) for what pruning removes
and keeps. `app.plan(prune=True)` and `app.deploy(prune=True)` are the SDK
forms, and both accept `workspace`. `--json` returns the typed plan or
deployment result, including the prune result when requested.

## lazycloud run

```bash
uv run lazycloud run HANDLER [ARGS]... [options]
```

Calls a decorated function remotely from your working tree, shows its progress
and logs, and prints the result. It needs no deploy first. JSON arguments
become Python values, and other arguments stay strings:

```bash
uv run lazycloud run quickstart:hello LazyCloud
uv run lazycloud run reports:summarize_sales '[1200, 3500, 800]'
```

Arguments are positional. Lists and objects need quoting so the shell passes
each as one argument.

Passing a pod starts an instance with a command. A plain Python callable runs
locally, so an example can coordinate remote calls from it. For objects with
`.run()` or `.remote()`, the CLI calls those methods.

Progress and remote logs go to stderr, and the result goes to stdout. See
[live progress](/concepts/tasks-and-logs#live-progress). Human output prints
Python results directly, including NumPy arrays and custom objects. `--json`
needs a JSON-compatible result and reports an output error for anything else.
`--output result.pkl` saves a Python result to a file.

## lazycloud serve

```bash
uv run lazycloud serve HANDLER [--timeout <seconds>] [--sync-dir <dir>]
```

Runs a function, endpoint, or ASGI app as a [live preview](/concepts/workflow#live-preview)
and streams its logs until Ctrl+C. `--sync-dir <dir>`, or `--sync`, syncs a
directory other than the current one. `--timeout 0`, the default, serves until
you interrupt it.

After an edit, `serve` transfers only the changed files. A file becomes visible
only after its checksum verifies. Large files transfer in chunks and need
temporary disk space locally and on the worker. [What gets uploaded](/concepts/workflow#what-gets-uploaded)
covers `.lazycloudignore`.

From Python, `.serve()` takes the same `timeout` and `sync_dir`:

```python
from page_stats import analyze

analyze.serve(sync_dir=".")
```

Functions, endpoints, ASGI apps, and apps all have `.serve()`. ASGI previews
run one HTTP worker so that source changes restart the application.

## lazycloud shell

```bash
uv run lazycloud shell HANDLER [--sync-dir <dir>] [options]
uv run lazycloud shell --container-id <id>
```

Opens an interactive shell in the handler's image, or attaches a shell to a
running container.

## lazycloud dev

```bash
uv run lazycloud dev [HANDLER] [--sync <dir>] [options]
```

Opens a shell in a remote container with your working directory synced in, for
iterating without a deploy. `--sync` defaults to `./`. Without a handler, `dev`
uses the managed Python image with default resources. A GPU or custom image
comes from a workload defined in code and passed as the handler.
