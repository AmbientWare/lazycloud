# Builds

LazyCloud builds your container images in the cloud using [Depot](https://depot.dev). No local Docker daemon required.

## How It Works

When you run `lazycloud deploy`, services with a `build` context are built remotely:

```yaml
services:
  api:
    build: ./api
    ports:
      - "8000:8000"

  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile.prod
    ports:
      - "3000:3000"
```

LazyCloud:
1. Uploads your build context to Depot
2. Builds the image using Depot's fast builders
3. Pushes the image to a private registry
4. Deploys the image to your service

## Why Depot?

- **Fast builds** — Native ARM and AMD64 builders with SSD storage
- **Shared caching** — Build layers are cached across deployments
- **No local Docker** — Build from any machine, even without Docker installed
- **Parallel builds** — Multiple services build simultaneously

## Pre-built Images

You can also use pre-built images from any registry:

```yaml
services:
  redis:
    image: redis:alpine

  postgres:
    image: postgres:16
```

These images are pulled directly without going through Depot.

<Tip>
For fastest deploys, use multi-stage Dockerfiles and order your layers from least to most frequently changed.
</Tip>

## Build Arguments

Build arguments let you pass values into your Dockerfile at build time. This is useful for variables that need to be embedded into your container image, like public API URLs for frontend apps.

### Defining Build Args

Define build arguments in your compose file under `build.args`. Use localhost defaults for local development:

```yaml
services:
  frontend:
    build:
      context: ./frontend
      args:
        # Localhost default for local `docker compose build`
        NEXT_PUBLIC_API_URL: http://localhost:8000

  api:
    build: ./api
    ports:
      - "8000:8000"
```

Then accept the argument in your Dockerfile:

```dockerfile
ARG NEXT_PUBLIC_API_URL
ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL

RUN npm run build
```

When you run `docker compose build` locally, it uses the localhost default. When you run `lazycloud deploy`, you'll be prompted to enter the production value.

<Note>
Build args are different from environment variables. Build args are available only during `docker build`, while environment variables are available at runtime. For Next.js apps, `NEXT_PUBLIC_*` variables must be build args because they're inlined into the JavaScript bundle.
</Note>

### The `.public` Suffix

When prompted for a build arg value, you can use `<service-name>.public` and LazyCloud will resolve it to the service's public URL:

```
? Enter value for NEXT_PUBLIC_API_URL: https://api.public
# Resolves to: https://api-abc12.lazycloud.dev
```

This also works in environment variables.

### Providing Build Arg Values

LazyCloud always prompts you to provide build arg values during deploy. You can provide them:

- **From a file** — `lazycloud deploy --build-arg .env.prod`
- **From your shell** — `lazycloud deploy --build-arg shell`
- **Manually** — Enter values one by one when prompted

Without the `--build-arg` flag, LazyCloud prompts you to choose a source interactively.

### When to Use Build Args vs Environment Variables

| Use Case | Solution |
|----------|----------|
| API keys, database URLs | Environment variables (runtime) |
| Public URLs for frontend apps | Build arguments (enter `https://<service>.public` when prompted) |
| Feature flags baked into the image | Build arguments |
| Configuration that can change without rebuild | Environment variables |

<Tip>
For server-side code, use the service name directly in environment variables (e.g., `redis:6379`). LazyCloud handles DNS resolution automatically.
</Tip>
