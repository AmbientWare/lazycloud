# Networking

Services communicate using their names as hostnames. You must define networks in your compose file for services to talk to each other.

## Networks Are Required

Services without a shared network cannot communicate. Define a network and assign services to it:

```yaml
services:
  api:
    build: .
    environment:
      - REDIS_URL=redis://cache:6379
      - DATABASE_URL=postgres://db:5432/app
    networks:
      - backend

  cache:
    image: redis:alpine
    networks:
      - backend

  db:
    image: postgres:16
    networks:
      - backend

networks:
  backend:
```

The `api` service can connect to `cache:6379` and `db:5432` because they all share the `backend` network.

<Warning>
If you don't define networks, your services will be isolated and unable to reach each other.
</Warning>

## Network Isolation

Use multiple networks to control which services can communicate:

```yaml
services:
  frontend:
    networks:
      - public

  api:
    networks:
      - public
      - internal

  db:
    networks:
      - internal

networks:
  public:
  internal:
```

In this setup:
- `frontend` can reach `api` (both on `public`)
- `api` can reach `db` (both on `internal`)
- `frontend` cannot reach `db` directly (different networks)

## External Access

Expose services to the internet with a custom domain:

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    labels:
      lazycloud.domain: myapp.example.com
```

LazyCloud automatically provisions TLS certificates for your domain.

<Note>
You'll need to point your domain's DNS to LazyCloud. See the deployment output for the exact DNS target.
</Note>

## Auto-Injected Service URLs

LazyCloud automatically injects environment variables for service discovery. Every service gets URL variables for all other services in the deployment:

| Variable | Example | Description |
|----------|---------|-------------|
| `LC_<SERVICE>_URL` | `http://api:8000` | Internal URL for service-to-service communication |
| `LC_<SERVICE>_PUBLIC_URL` | `https://api-abc12.lazycloud.dev` | Public URL (only for services with exposed ports) |

Service names are uppercased and hyphens are replaced with underscores. For a service named `my-api`, you get `LC_MY_API_URL` and `LC_MY_API_PUBLIC_URL`.

### Using LC_* Variables in Compose

You can reference these variables in your compose file with defaults for local development:

```yaml
services:
  frontend:
    build: ./frontend
    ports:
      - "3000:3000"

  api:
    build: ./api
    ports:
      - "8000:8000"
    environment:
      # Uses LC_REDIS_URL in cloud, falls back to default locally
      - REDIS_URL=${LC_REDIS_URL:-redis://redis:6379}

  redis:
    image: redis:7-alpine
```

At runtime, the `frontend` service automatically has access to:
- `LC_API_URL` → `http://api:8000`
- `LC_API_PUBLIC_URL` → `https://api-abc12.lazycloud.dev`
- `LC_FRONTEND_URL` → `http://frontend:3000`
- `LC_FRONTEND_PUBLIC_URL` → `https://frontend-abc12.lazycloud.dev`
- `LC_REDIS_URL` → `http://redis:6379`

<Tip>
Use `LC_*_URL` for server-side API calls between your services. Use `LC_*_PUBLIC_URL` when you need the external URL, such as for OAuth callbacks or webhooks.
</Tip>

<Note>
For client-side JavaScript (like Next.js `NEXT_PUBLIC_*` variables), you can reference `LC_*_PUBLIC_URL` as a build argument. LazyCloud will auto-resolve it:

```yaml
build:
  args:
    NEXT_PUBLIC_API_URL: ${LC_API_PUBLIC_URL:-http://localhost:8000}
```
</Note>

## Cross-Deployment Communication

Services in different deployments (different compose files) cannot communicate directly. Each deployment is isolated to its own network space.

If you need services to communicate across deployments, expose them via domains and use HTTP/HTTPS.
