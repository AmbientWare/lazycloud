# Networking

Services communicate using their names as hostnames. You must define networks in your compose file for services to talk to each other.

## Networks Are Required

Services without a shared network cannot communicate. Define a network and assign services to it:

```yaml
services:
  api:
    build: .
    environment:
      - REDIS_URL=redis://cache:6379
      - DATABASE_URL=postgres://db:5432/app
    networks:
      - backend

  cache:
    image: redis:alpine
    networks:
      - backend

  db:
    image: postgres:16
    networks:
      - backend

networks:
  backend:
```

The `api` service can connect to `cache:6379` and `db:5432` because they all share the `backend` network.

<Warning>
  If you don't define networks, your services will be isolated and unable to
  reach each other.
</Warning>

## Network Isolation

Use multiple networks to control which services can communicate:

```yaml
services:
  frontend:
    networks:
      - public

  api:
    networks:
      - public
      - internal

  db:
    networks:
      - internal

networks:
  public:
  internal:
```

In this setup:

- `frontend` can reach `api` (both on `public`)
- `api` can reach `db` (both on `internal`)
- `frontend` cannot reach `db` directly (different networks)

## External Access

Expose services to the internet with a custom domain:

```yaml
services:
  web:
    build: .
    ports:
      - '3000:3000'
    labels:
      lazycloud.domain: myapp.example.com
```

### DNS Setup

Add a CNAME record pointing your custom domain to LazyCloud:

| Type  | Name                | Target          |
| ----- | ------------------- | --------------- |
| CNAME | `myapp.example.com` | `lazycloud.dev` |

SSL certificates are provisioned automatically once the CNAME is configured.

## Request Size Limits

LazyCloud allows request bodies up to **128 MB**. This covers most use cases including:

- Image uploads
- File attachments
- Document uploads
- Form submissions with media

<Tip>
  For very large file uploads (videos, datasets), consider using presigned URLs
  to upload directly to object storage instead of proxying through your
  application.
</Tip>

<Note>If your application requires a higher limit, contact support.</Note>

## Service Discovery

### Internal Communication

For service-to-service communication within your deployment, use the service name directly as the hostname. LazyCloud automatically resolves service names:

```yaml
services:
  api:
    build: ./api
    ports:
      - '8000:8000'
    environment:
      - REDIS_URL=redis://redis:6379
      - DATABASE_URL=postgres://db:5432/app

  redis:
    image: redis:7-alpine
    expose:
      - '6379'

  db:
    image: postgres:16
    expose:
      - '5432'
```

The `api` service can connect to `redis:6379` and `db:5432` directly. No special configuration needed.

<Tip>
  Use `expose` for internal-only services (like databases). Use `ports` for
  services that need external access.
</Tip>

### Public URLs with `.public` Suffix

When you need a service's public URL (for OAuth callbacks, webhooks, or client-side code), use the `.public` suffix. LazyCloud transforms these at deploy time:

```yaml
services:
  frontend:
    build: ./frontend
    ports:
      - '3000:3000'
    environment:
      # Transforms to: https://api-abc12.lazycloud.dev
      - API_PUBLIC_URL=https://api.public

  api:
    build: ./api
    ports:
      - '8000:8000'
    environment:
      # Internal: use service name directly
      - REDIS_URL=redis://redis:6379
      # Public: use .public suffix
      - CALLBACK_URL=https://api.public/auth/callback
```

The `.public` suffix works in both environment variables and build args:

```yaml
build:
  args:
    # For client-side JavaScript (NEXT_PUBLIC_*, etc.)
    NEXT_PUBLIC_API_URL: https://api.public
```

<Note>
  The `.public` suffix only works for services with exposed `ports`.
  Internal-only services (using `expose`) don't get public URLs.
</Note>

## Cross-Deployment Communication

Services in different deployments (different compose files) cannot communicate directly. Each deployment is isolated to its own network space.

If you need services to communicate across deployments, expose them via domains and use HTTP/HTTPS.
