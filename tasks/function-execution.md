# Function execution: first slice

Outcome: on a local machine, `lazycloud deploy reports` followed by
`summarize_sales.remote([1200, 3500, 800])` returns the value, streams the
function's output to the caller and scales the container back to zero. The same
path proves admission, placement, host startup, execution, retries,
cancellation, timeouts and host loss against real PostgreSQL, an S3 object
store and Docker.

This file is the integrator's contract for the slice. Owners propose changes to
the shared files named here; they do not edit them concurrently.

## Findings from the reference

The reference trace (9e259ce75) shows what this slice removes:

- A function definition is a mutable `stubs` row with about 60 columns that
  duplicate its JSON configuration. Deploy spans four transactions with
  compensation, and three sources name the current release.
- Cold invoke runs about six transactions and five to seven Redis calls, checks
  billing twice and writes five to seven event rows per task.
- Inputs, upstream results and results live inline on the hot `tasks` row and
  are rewritten by every upsert.
- Container state is held in both Redis and Postgres, as are the ready queue and
  worker capacity. Capacity reservations live only in Redis.
- Four authorities describe a worker or host. Redis cadence keys gate recovery,
  so a Redis outage stops timeouts and retries.
- The runner holds a 24-hour workspace token and calls the public API to claim,
  log, finish, retire and poll for cancellation every 250 ms. Cancellation
  works only in process-slot mode.
- Stale transitions can overwrite finished tasks, and reclaimed attempts keep
  their original start time.

## Decisions

- Wakes use PostgreSQL `NOTIFY`, which is delivered on commit. The slice uses no
  Redis. Channels: `lc_host` (host id), `lc_execution` (release id),
  `lc_task` (task id) and `lc_claim` (release id).
- A release is immutable. Deploy runs one transaction: it locks the workload,
  inserts the next version and switches `active_release_id`. An identical spec
  digest reuses the active release.
- A task is pinned to the release that was active when it was admitted.
  Containers belong to one release. Execution drains containers of a release
  that has no queued or running tasks.
- Inputs and results live in `task_inputs` and `task_results`, each written
  once and capped at 16 MiB. The task row stays small.
- Terminal task statuses are `succeeded`, `failed` and `cancelled`. The failure
  object carries its kind: `user_error`, `load_error`, `timeout`, `lost`,
  `start_failed` or `system`. A retry waits as `queued` with a future
  `available_at`.
- Containers move through `pending`, `starting`, `ready`, `draining` and
  `stopped`. A container row is placed once. After host loss, execution creates
  a new container if demand remains, so the container id is the fencing
  identity.
- Attempt ids fence completions. A completion is accepted only when the attempt
  is `running` and its container is assigned to the calling host.
- The agent claims tasks for its containers over the host connection. Containers
  hold no platform credential. In-container SDK calls are an explicit gap.
- `supervisor` is PID 1 in every container. The agent bind-mounts it with the
  managed Python runtime. The supervisor runs one runner process per slot,
  captures its stdout and stderr per attempt, and kills the slot's process group
  on cancellation or timeout. It reports results over a Unix socket that the
  agent serves per container. The container boundary justifies a fourth binary.
- The local runner protocol (supervisor to runner) uses length-prefixed frames
  on an inherited file descriptor. Each frame is a JSON header plus an optional
  raw payload, so pickles are not base64-encoded.
- A container that fails to import its handler reports `load_error`. Execution
  then fails the release's queued tasks with that error rather than retrying
  the same import. Three consecutive `start_failed` containers on one release
  fail its queued tasks the same way.
- Workspaces have globally unique names and appear in every public path.
- IDs are UUIDv7 values generated by PostgreSQL 18 `uuidv7()`. The API renders
  them as canonical UUID strings, and Go owners wrap them in typed IDs.
- Tokens are 32 random bytes with a `lc_` prefix. The database stores their
  SHA-256, which needs no password hashing at this entropy.

## Workflow and invariants

| Step | Owner | Transaction and invariant |
| --- | --- | --- |
| Source upload | storage | `source_objects` records a verified `(workspace, sha256)`. Presigned PUT; the server checks the object size on registration |
| Deploy | control | Locks the workload row; versions are monotonic; the release insert and `active_release_id` switch commit together |
| Submit | execution | Locks the workload `FOR UPDATE`; `max_pending_tasks` counts queued tasks under that lock; tasks and inputs insert in one batch; `NOTIFY lc_execution` and `lc_claim` |
| Plan | execution (scheduler) | `pg_try_advisory_xact_lock('execution-planning')`: one planner creates containers, so `max_containers` holds. Desired = clamp(ceil((queued + running) / tasks_per_container), min, max); min applies only to the active release |
| Drain idle | execution (scheduler) | Conditional update: `ready` to `draining` only with no running attempt and the last attempt finished more than `keep_warm_seconds` ago |
| Place | scheduling (scheduler) | `pg_try_advisory_xact_lock('placement')`: host capacity is never oversubscribed. Pending containers are ordered by per-workspace round robin; assignment sets `host_id` and `starting`, then `NOTIFY lc_host` |
| Start | host runtime | Server derives `StartContainer` from rows in `starting`; commands are idempotent by container id and recomputed after reconnect |
| Ready | execution (server) | `starting` to `ready` only when the host matches |
| Claim | execution (server) | Container `FOR SHARE` in `ready` on the calling host; tasks `FOR UPDATE SKIP LOCKED` ordered by `available_at`; attempt rows and deadlines insert in the same transaction |
| Complete | execution (server) | Attempt `FOR UPDATE` in `running` on the calling host; success writes the result; failure applies the retry policy; `NOTIFY lc_task` and `lc_host` |
| Cancel | execution (server) | Queued: cancelled at once. Running: attempt `cancelled`, task `cancelled`, `NOTIFY lc_host` so the host kills the slot. A late completion is stale |
| Timeout | execution (scheduler) | Running attempts past `deadline_at`: `timed_out`, retry policy, `NOTIFY lc_host` |
| Host loss | compute + execution (scheduler) | One coordinated transaction: hosts with `last_seen_at` older than 30 s become `lost`, their containers `stopped(host_lost)`, running attempts `lost` and retried |
| Exit | execution (server) | Container `stopped`; running attempts `lost` and retried; `load_error` fails the release's queued tasks |

Retries apply to `user_error`, `timeout` and `lost` while `attempt_count <
max_attempts`. The delay follows the release's retry policy. `load_error`,
`cancelled` and exhausted attempts are terminal.

## Work packets

Every packet works on its own branch and worktree based on `foundation`. It keeps
generated code current and runs gofmt, go vet, `go tool golangci-lint run` and
`go test -race` on its packages against `compose.test.yaml`.

1. Server: `internal/identity`, `internal/control`, `internal/storage`,
   `internal/execution` (admission, claims, completion, cancellation, container
   reports), `internal/api`, `internal/hostsession`, `cmd/server`. Admin
   subcommands on `cmd/server` bootstrap users, workspaces, tokens and host join
   tokens.
2. Scheduler: `internal/execution` (planning, draining, deadlines, host-loss
   release), `internal/scheduling`, `internal/compute` (enrollment, liveness,
   capacity), `cmd/scheduler`.
3. Host runtime: `internal/agent`, `internal/supervisor`, `cmd/agent`,
   `cmd/supervisor`, the managed runtime build.
4. Python: SDK and CLI on the new public API, runner on the local runner
   protocol, generated Pydantic models, deletion of superseded shared models.

Owner package conventions:

- Queries live in `internal/<owner>/queries/*.sql` with
  `internal/<owner>/sqlc.yaml` (template below) and a
  `//go:generate go tool sqlc generate` directive. sqlc writes into the owner
  package with `omit_unused_structs`, so generated rows serve as domain types
  where the meanings match.
- The server validates requests against the embedded OpenAPI document with
  `github.com/oapi-codegen/nethttp-middleware`, so handlers do not restate
  schema limits.
- Tests use `dbtest.New(t)` for an isolated migrated database.
- An owner's type is named after its package and built by `New<Owner>`
  (`execution.NewExecution`), because sqlc's `New` builds `Queries`.
- `Execution.finishAttempt` is the single transition from a running attempt to
  a task outcome. Completion, timeouts, container exits and host loss all call
  it. `Execution.containerExited` is the single container stop transition:
  reports, start timeouts and host loss call it. Lock order is container,
  then task, then attempt; no transaction locks a container after a task.

```yaml
version: "2"
sql:
  - engine: postgresql
    schema: ../../migrations
    queries: queries
    gen:
      go:
        package: <owner>
        out: .
        sql_package: pgx/v5
        emit_pointers_for_null_types: true
        omit_unused_structs: true
        output_db_file_name: queries_db.go
        output_models_file_name: queries_models.go
        overrides:
          - db_type: uuid
            go_type: github.com/google/uuid.UUID
          - db_type: uuid
            nullable: true
            go_type: { import: github.com/google/uuid, type: UUID, pointer: true }
          - db_type: timestamptz
            go_type: time.Time
          - db_type: timestamptz
            nullable: true
            go_type: { type: time.Time, pointer: true }
```

Packets 1 and 2 share `internal/execution`. Each adds its own files and its own
`queries/*.sql`, and uses the shared types in `internal/execution/types.go`.

## Integrated evidence

The measurements below come from one local host (24 CPUs, Docker 29, runc).
The same SDK script ran against server, scheduler and agent processes with
PostgreSQL 18 and Garage.

| Scenario | Result |
| --- | --- |
| Deploy of a three-function app | 0.65 s from the CLI |
| Cold `.remote()`: admission, placement, image present, container ready, result | 0.9 to 1.1 s |
| Container assigned to ready (supervisor, runner import, handler load) | 0.85 to 1.3 s |
| Warm `.remote()` round trip | p50 9 to 14 ms, p95 12 to 18 ms |
| `.map()` over 200 inputs, max 8 containers | 0.9 to 1.3 s |
| `.map()` over 2,000 inputs, max 8 containers | 4.6 to 4.9 s |
| Planning plus placement for 2,000 queued tasks, 50 containers, 5 hosts | 5.3 ms (scheduler benchmark) |
| User exception | Re-raised as the original class with its message |
| `timeout_seconds=2` | Fails as `timeout` 3.7 s after submit, cold start included |
| Idle containers | Drain after `keep_warm_seconds` and stop |

Defects found by the integrated run and fixed:

- A Unix socket under a deep state directory exceeded `sun_path`. The agent
  now keeps link sockets in a short socket directory.
- The agent freed a slot before the server recorded its completion, so the
  next claim saw a full container and waited 20 s for a wake that never came.
  The slot is now freed after `CompleteTask` returns.
- Containers were hard-limited to their reservation, which made a 0.125-CPU
  cold import take 6 s. As in the reference, reservations are now CPU shares
  and `memory.low`, with burst ceilings: the CPU reservation plus 16 cores
  capped at the host, and memory at the stated limit or four times the
  reservation, bounded to 1 to 8 GiB above it.

## Intentional differences from the reference

- A task's failure is a typed object (`kind`, `type`, `message`, `traceback`,
  serialized exception), and the SDK re-raises the original exception. The
  reference returned only `"Type: message"`.
- A handler import error fails the release's queued tasks immediately instead
  of retrying the import per task.
- Containers hold no platform credential.
